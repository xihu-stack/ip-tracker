# IP 定位追踪平台 · 运维手册

面向服务器管理员的日常运维文档。部署方式见根目录 `README.md`，本手册覆盖部署之后的全部运维操作。

---

## 1. 系统架构速览

| 组件 | 说明 |
|------|------|
| 后端 | FastAPI + SQLite，systemd 服务名 `ip-tracker`，监听 **8000** |
| 前端 | Vue 3 静态文件（`frontend/dist/`），由后端直接托管，无需单独进程 |
| 上报入口 | Nginx 监听 **9000**，**仅放行 `/api/report`**，其余路径 403 |
| 客户端 | Windows 计划任务 `Company_IP_Tracker`，每 10 分钟上报一次 |
| 数据文件 | SQLite 单文件：`/opt/ip-tracker/ip_tracker.db` |
| 定位数据源 | cip.cc（主）+ pconline（备用），自动切换 |

关键路径：

```
/opt/ip-tracker/                 # 应用根目录（systemd WorkingDirectory）
├── server/                      # 后端代码
│   ├── main.py                  # 入口
│   ├── auth.py                  # JWT 密钥、密码哈希
│   ├── services/ip_location.py  # IP 归属地解析
│   └── services/city_coords.py  # 城市经纬度对照表
├── frontend/dist/               # 前端静态文件（构建产物，随仓库提交）
├── venv/                        # Python 虚拟环境
└── ip_tracker.db                # ⭐ 全部业务数据（employees / ip_records / admins）

/etc/systemd/system/ip-tracker.service    # 服务单元
/etc/nginx/conf.d/ip-tracker.conf         # 9000 上报口配置
```

## 3. 账号与密码

- 首次启动自动创建默认管理员 `admin / admin123`，**部署后第一时间修改**。
- 页面修改：登录后台 → 右上角用户菜单 → 修改密码（调 `PUT /api/change-password`）。
- 修改后所有已登录会话仍有效（JWT 有效期 24 小时），到期需用新密码重新登录。

### 忘记密码：命令行重置

在服务器上执行（把 `NewPass@123` 换成新密码）：

```bash
cd /opt/ip-tracker
venv/bin/python - <<'EOF'
import sys
sys.path.insert(0, 'server')
from auth import hash_password
from database import SessionLocal
from models import Admin

db = SessionLocal()
a = db.query(Admin).filter_by(username='admin').first()
if not a:
    a = Admin(username='admin', hashed_password='')
    db.add(a)
a.hashed_password = hash_password('NewPass@123')
db.commit()
print('密码已重置')
EOF
```

> 必须在 `/opt/ip-tracker` 目录下运行——数据库路径是相对路径，换目录会新建一个空库。密码要求包含大小写字母、数字和特殊符号（示例格式：`Xk9#mP2v`）。

### JWT 密钥说明

JWT 签名密钥在**首次启动时自动随机生成**，保存在 `server/.secret_key`（权限 600，已加入 .gitignore）。

- **不要删除**该文件——删除后密钥重新生成，所有管理员需重新登录（客户端上报不受影响）
- 可用环境变量 `IP_TRACKER_SECRET_KEY` 覆盖（systemd 里加 `Environment=` 后 restart 生效）

## 3.1 上报接口加锁（可选，分阶段启用）

`/api/report` 默认**不校验**任何令牌，已部署的客户端不受影响。如需防止外部伪造上报，按以下顺序操作：

```text
第一步：改造后的 client/deploy.ps1 里 $REPORT_TOKEN 填入随机令牌（如 openssl rand -hex 16 生成），
        重新推送给全部员工电脑（老客户端继续无令牌上报，不受影响）
第二步：确认后台员工列表里设备都在正常上报（日志出现 X-Report-Token 即为新版客户端）
第三步：服务器开启校验——编辑 /etc/systemd/system/ip-tracker.service，在 [Service] 段加一行：
        Environment=IP_TRACKER_REPORT_SECRET=同样的令牌
        然后 systemctl daemon-reload && systemctl restart ip-tracker
```

开启后：带正确令牌的请求正常；不带或令牌错误的请求返回 403。中途有老客户端漏推，表现为该设备离线，补推新版 deploy.ps1 即恢复。

## 3.2 SSO 统一门户登录（OAuth2，可选）

系统支持标准 OAuth2 授权码流程，可接入 Keycloak / Authentik / Casdoor / Authing / **企业自建 SSO** 等。**不配置时完全不影响现有账号密码登录。**

### 配置方式（推荐：管理后台页面）

登录后台 → **系统设置** → 填写 SSO 端点信息 → 保存（**立即生效，无需重启服务**）：

| 配置项 | 说明 |
|--------|------|
| 启用开关 | 总开关 |
| 授权地址 / Token 地址 / 用户信息地址 | 企业 SSO 的三个 OAuth2 端点 |
| 客户端 ID / 密钥 | 在企业 SSO 侧创建应用后获得 |
| 用户名字段 | 自建 SSO 的用户名字段各不相同（account / loginName / userid…），默认自动识别，登录报"没有可用的用户名"时在此指定 |

页面上还提供：**回调地址一键复制**（在企业 SSO 侧创建应用时填它，形如 `http://<后台地址>:8000/api/auth/callback`）、**测试连接**（逐个探测端点连通性）、**打开 SSO 登录实测**。

### 备用配置方式（配置文件/环境变量）

后台页面配置保存在数据库中优先生效；也可用 systemd 环境变量兜底（改完需重启）：

> 注意：环境变量启用的 SSO，一旦在系统设置页保存过任何配置，就改为以页面配置为准（页面会显示"由环境变量启用"的提示条；关闭开关保存前会弹确认）。

```ini
# /etc/systemd/system/ip-tracker.service 的 [Service] 段（或 /opt/ip-tracker/app.env 文件）
Environment=OAUTH_ENABLED=1
Environment=OAUTH_CLIENT_ID=客户端ID
Environment=OAUTH_CLIENT_SECRET=客户端密钥
Environment=OAUTH_AUTH_URL=https://sso.example.com/authorize
Environment=OAUTH_TOKEN_URL=https://sso.example.com/token
Environment=OAUTH_USERINFO_URL=https://sso.example.com/userinfo
```

### 门户登出回调（踢下本系统会话）

在认证中心「应用管理 → 编辑应用 → 登出回调地址」填：

```
http://iptracker.huashen.bio:8000/api/auth/logout-notify
```

员工在门户退出时，认证中心会 POST 通知本系统（`{"username":"...","logoutAt":...}`），
本系统随即吊销该用户所有已签发的本地令牌（JWT 无状态，通过"吊销时间点"实现），
用户浏览器在 30 秒轮询内自动回到登录页。不登记此回调也不影响主流程，只是门户退出后
本系统的会话要等到自然过期（最长 24 小时）。

### 谁能登录：两层控制

| 层 | 在哪配置 | 说明 |
|----|----------|------|
| 第一层（主控制） | 企业 SSO 管理后台 | 创建本应用时把**授权范围**限制到指定用户/部门/组，SSO 侧不放行的人根本到不了登录页 |
| 第二层（兜底） | 本系统「系统设置」 | **SSO 访问白名单**：允许的用户名列表 + 允许的邮箱后缀，命中任一即放行 |

白名单规则：**两个名单都留空 = 不限制**（所有能通过 SSO 认证的人都能登录，注意敏感数据风险）；配置后不在名单内的 SSO 用户即使认证通过也会被拒绝（不开户、页面提示无权访问）。

### 行为说明

- **SSO 启用后**：未登录访问任何页面都会自动跳转统一门户（登录页停留约 1 秒即跳转，不暴露密码表单），登录后自动回到原页面
- **管理员密码入口是独立路径 `/admin-login`**（如 `http://<服务器IP>:8000/admin-login`），仅管理员使用、不对外公布；SSO 故障或本地 admin 账号从这里登录
- **SSO 未启用时**：`/login` 和 `/admin-login` 均为账号密码登录
- SSO 用户**首次登录自动开户**（无需预先创建；该账号不能用密码登录）
- 访问控制见下方"谁能登录：两层控制"
- 本系统"退出登录"只清除本系统会话，**不会登出统一门户**
- 本地开发可用 `server/fake_sso.py` 模拟 SSO 服务器做全流程测试


## 4. 数据备份与恢复

所有业务数据都在一个 SQLite 文件里，备份它就备份了一切。

### 手动备份

```bash
cd /opt/ip-tracker
sqlite3 ip_tracker.db ".backup /root/backup/ip_tracker_$(date +%F).db"
```

（`sqlite3 .backup` 是在线备份，不必停服务；没有 sqlite3 命令时，先 `systemctl stop ip-tracker` 再直接 `cp`，完成后 `start`。）

### 自动每日备份（保留 14 天）

```bash
sudo crontab -e
# 加入一行（每天 02:30 备份）：
30 2 * * * mkdir -p /root/backup && sqlite3 /opt/ip-tracker/ip_tracker.db ".backup /root/backup/ip_tracker_$(date +\%F).db" && find /root/backup -name "ip_tracker_*.db" -mtime +14 -delete
```

### 恢复

```bash
systemctl stop ip-tracker
cp /root/backup/ip_tracker_2026-08-16.db /opt/ip-tracker/ip_tracker.db
systemctl start ip-tracker
```

## 4.1 数据保留期（自动清理）

install.sh 会注册 `ip-tracker-retention.timer`（每周日 03:00 执行），自动删除 **365 天之前**的 IP 历史记录（只清 ip_records，设备台账不动）：

```bash
systemctl list-timers | grep retention     # 查看下次执行时间
systemctl cat ip-tracker-retention.service # 查看/修改保留天数（IP_TRACKER_RETENTION_DAYS）
# 手动立即清理一次（示例改为保留 90 天）：
cd /opt/ip-tracker && IP_TRACKER_RETENTION_DAYS=90 venv/bin/python retention.py
```

> git pull 更新到含此功能的版本后，需要重跑一次 `sudo bash install.sh` 来注册 timer（数据不受影响）。

## 4.2 上报口 HTTPS（enable_https.sh）

```bash
sudo bash enable_https.sh report.example.com admin@example.com
```

自动完成：安装 certbot → 签发 Let's Encrypt 证书 → 9000 口改为 HTTPS（仍只放行 `/api/report`）→ 注册续期钩子。**已部署的 HTTP 客户端不用动**——nginx 会用 307 跳转自动把 http 请求转到 https（保留 POST）。要求：域名已解析到服务器、80 端口公网可达（签发/续期用）。

## 5. 版本升级

```bash
cd /opt/ip-tracker
git pull                        # 拉取最新代码（前端 dist 构建产物随仓库提交，无需在服务器上 npm build）
sudo systemctl restart ip-tracker
```

验证：`journalctl -u ip-tracker -n 20` 无报错，浏览器打开后台页面正常。

升级不会动数据库；`main.py` 启动时自动做增量迁移（如补 `last_seen_at` 字段）。保险起见，升级前先做一次 §4 的备份。

## 6. 修改前端并重新构建

cd frontend

## 8. 故障排查

| 现象 | 排查步骤 |
|------|----------|
| 后台打不开（8000） | `systemctl status ip-tracker` → 起不来看 `journalctl -u ip-tracker -n 50`；起了但访问不了查防火墙是否放行 8000 |
| 客户端显示离线 | 在线阈值为 **20 分钟**无上报即离线。先在终端按 §7 验证计划任务；终端正常再看服务器 `access.log` 有无上报记录 |
| 上报返回 403 | 走的是 9000 端口但路径不是 `/api/report`，检查 `deploy.ps1` 里 `$SERVER_URL` 是否以 `/api/report` 结尾 |
| 上报超时/连不上 | 终端 `Test-NetConnection <服务器公网IP> -Port 9000`；服务器查云安全组 + `firewall-cmd`/`ufw` 是否放行 9000 |
| 地图空白 | 浏览器 F12 看 `/china.json` 与 `/api/map-data` 是否 200；地图数据来自前端自带的 `china.json`，与外网无关 |
| 归属地异常/显示"未知" | cip.cc 被限流时自动切 pconline 备用源；仍异常等几分钟再试。历史数据可批量修正：`cd /opt/ip-tracker && venv/bin/python server/cleanup_geo.py` |
| 员工"最后上报时间"不对 | 该时间来自服务器时钟，确认服务器时区与时间正确：`timedatectl` |
| 改了代码不生效 | 前端是构建产物，改 `src` 必须重新 `npm run build`（§6）；浏览器有缓存时 Ctrl+F5 |
| 不确定服务器跑的哪个版本 | `curl http://127.0.0.1:8000/api/version`，或看后台侧边栏底部的 v 号 |

## 11. IP 归属地精准化

归属地解析默认策略：**人工映射 → 三源并发交叉校验（cip.cc / pconline / ip-api.com）→ 城市坐标表**。同一 IP 结果缓存 1 小时，重复上报不会重复查询外部数据源。

**人工映射（100% 准确）**：企业固定出口（办公点专线、VPN 出口）在「系统设置 → IP 归属地人工映射」钉住城市，每行一条 `IP或网段 城市名`（如 `203.0.113.5 上海`、`10.8.0.0/24 江苏-苏州市`，支持 `#` 注释行），保存后约 30 秒生效，命中的 IP 不再走在线查询。城市名建议从员工列表的当前城市复制以保证格式一致。

**异常城市拦截与体检**：所有城市值入库前经过合法性校验（全中文或全英文城市名，
乱码碎片如 'Ϻ'/'M和' 一律记"未知"）。「系统设置 → 归属地数据体检」可查看历史数据中的
异常数量并**一键修正**（后台自动重新解析这些 IP，无需登录服务器跑脚本）。

**交叉校验**：三个数据源并发查询，两个及以上源给出相同城市时采纳共识，减少单个 IP 库登记错误；无共识时按源优先级（cip.cc > pconline > ip-api）取用。

手工测试上报：

```bash
curl -X POST http://<服务器IP>:9000/api/report \
  -H "Content-Type: application/json" \
  -d '{"hostname":"test-pc","ip":"1.2.3.4"}'
```
